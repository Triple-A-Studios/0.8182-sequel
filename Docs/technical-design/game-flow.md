# Game Flow (Feel polish, Pass 5)

Wires the menu→game transition Pass 4 left stubbed. Three scenes now: `Bootstrap.unity` (index 0, new), `MainMenu.unity` (index 1), `Prototype.unity` (index 2) — reordered in `ProjectSettings/EditorBuildSettings.asset`.

## Why not defer scene activation

An earlier draft of this pass used `AsyncOperation.allowSceneActivation = false` to keep `Prototype.unity`'s objects from existing at all until Play was pressed — the standard Unity pattern for "no loading screen." Rejected: the actual vision has the equipped `Plane` visible and idle on the menu itself (through the mockup's transparent center 3D slot — idle bob/dust puffs is future art work, not this pass), then visibly flying off into the run on Play, Subway Surfers-style. That requires `Prototype.unity`'s systems to exist and render *while the player is still on the menu*, so the gate had to move from the scene-loading level to the **game-state level**.

## Bootstrap

`Assets/_Project/Scripts/Bootstrap/BootstrapLoader.cs` — `Awake()` sets `GameManager.ManagedByBootstrap = true` (a plain static flag, read synchronously by `GameManager.Awake()` — see below) and `DontDestroyOnLoad`s itself, *before* either scene load starts. Then `async void Start()` loads `MainMenu` and `Prototype` additively together, polls an `AsyncOperationGroup` (`operations`) until both report done, and calls `SceneManager.SetActiveScene(Prototype)` (so lighting/skybox and any `GetActiveScene()`-based logic resolve to the scene that actually has an environment, not the camera-less menu).

Structure adapted from `C:\GitHub\Unity\Utils\Assets\TripleA\TripleA-SceneManager` (read for reference at the developer's request, not installed as a dependency — it uses Addressables + `Eflatun.SceneReference`, both explicitly ruled out). That package's additive `SceneGroupManager<T>` generalizes over an arbitrary, `Enum`-keyed set of scene groups; none of that generality is ported here since this project has exactly one fixed pair of scenes to load, not a general multi-group system. What *is* adopted: `AsyncOperationGroup` (`Assets/_Project/Scripts/Bootstrap/AsyncOperationGroup.cs`) ported near-verbatim — it's pure `UnityEngine.AsyncOperation`, already zero-Addressables in the original — and the `async`/`Task`-polling shape (the reference's own sample uses `private async void Start()` the same way). `AsyncOperationGroup.Progress` isn't consumed by anything yet (no loading UI this pass) but costs nothing to keep for when the fuller bootstrap scene the developer has planned (leaderboard init, other services, an actual loading screen) needs one.

## `GameManager`'s state machine

Uses the FSM package the developer installed, `com.triple-a-studios.statemachine` (`TripleA.StateMachine.FSM`) — plain C#, no `MonoBehaviour`, predicate-driven: `StateMachine.AddTransition(from, to, IPredicate)` auto-fires the transition once its predicate evaluates true during `OnUpdate()` (registering a transition also registers both its states as a side effect — required before `SetState` can target them). States implement `IState`/`BaseState` (`OnEnter`/`OnUpdate`/`OnFixedUpdate`/`OnLateUpdate`/`OnExit`).

Two states, `Assets/_Project/Scripts/Game/States/MainMenuState.cs` / `PlayingState.cs` — each holds a `GameManager` reference and calls back into it from `OnEnter` (`RaiseReturnedToMenu()` / `RaiseRunStarted()`). The states are pure notifiers; `GameManager` owns the actual `RunStarted`/`ReturnedToMenu` events and the two flags (`m_playRequested`/`m_menuRequested`) the transitions poll. `EnterPlayingState()`/`EnterMainMenuState()` just flip a flag rather than calling `SetState` directly — the transition fires on the *next* `Update` (`GameManager.Update()` now ticks `m_stateMachine.OnUpdate()`), a one-frame delay that's imperceptible for a UI button click or a startup sequence a real build's splash screen already covers.

**Minimal-gate scope** (developer's explicit call, not a full centralized-tick rewrite): every other gameplay system keeps its own `Update`/`FixedUpdate` unchanged. `PlaneController`, `FuelSystem`, and `SpawnManager` — the three with continuous time-based behavior that would visibly "leak" before Play (movement, fuel drain, spawning) — get enabled/disabled based on state, and that's `PlayerManager`'s job (see below), not something these three systems know about themselves. `HealthSystem`/`ScoreSystem`/`AltitudeSystem`/`LateralSystem` are event/passive-driven and don't need gating — nothing bad happens if they exist but nothing is triggering them. The `HUD` GameObject gets the same treatment for a different reason: it shares the same UI Toolkit `PanelSettings` as `MainMenu`'s own UI (both use `FuelGaugePanelSettings.asset`), so with both scenes loaded, the HUD renders directly over the menu unless something hides it — confirmed as a second bug alongside the plane-moving one during testing, fixed by folding `HUD` into the same `PlayerManager` gate as the other three.

### Choosing the initial state: `GameManager.ManagedByBootstrap`

`Prototype.unity` has two legitimate entry paths: through `Bootstrap` → `MainMenu` → Play (the new normal flow), and standalone — opening `Prototype.unity` directly and pressing Editor Play, which is how every earlier pass in this milestone was tested, and how `GameOverUI`'s Restart button already works (`SceneManager.LoadScene(SceneManager.GetActiveScene().buildIndex)`, a single-mode reload of just `Prototype.unity`). Neither should require a menu to exist, and standalone testing/Restart must default straight into `PlayingState`.

**First cut (reverted after developer testing): default to `PlayingState` always, `Bootstrap` explicitly calls `GameManager.EnterMainMenuState()` once it confirms both scenes are loaded.** This looked sound on paper (`Bootstrap` waits on both `AsyncOperation`s before doing anything) but broke in practice: `MainMenu` and `Prototype` load via two independent async operations with no guaranteed relative completion order, so `Prototype`'s own `GameManager.Awake()` can — and did — run and default to `Playing` several frames *before* `Bootstrap`'s polling loop finishes and gets around to calling `EnterMainMenuState()`. In that window `PlaneController`/`FuelSystem`/`SpawnManager` were enabled (the Playing default) and the HUD was active — confirmed bugs: the plane visibly moved forward and the HUD rendered over the menu before Play was ever pressed. `EnterPlayingState()`/`EnterMainMenuState()`'s one-frame-poll delay (see above) only ever affects *transitions after the initial state settles* — it was never a safe mechanism for the *initial* state itself, which needed to be correct from `GameManager`'s very first `Awake()`, not "eventually, once an async chain catches up."

**Fixed: `public static bool GameManager.ManagedByBootstrap`**, set by `BootstrapLoader.Awake()` — a plain static flag, not an async signal, so there's no window to fall through. `Bootstrap`'s `Awake()` always runs before it kicks off any scene load, so the flag is reliably `true` by the time `Prototype.unity`'s `GameManager.Awake()` ever runs, regardless of which scene's load happens to finish first. `GameManager.Awake()` reads it once to pick its initial `SetState` call and immediately resets it to `false` (**consume-once**) — this is what makes Restart still work correctly: `DontDestroyOnLoad` means the same `BootstrapLoader` instance survives a Restart's single-mode reload of `Prototype.unity`, but its `Awake()` doesn't run again (same object, not recreated), so the flag stays at `false` (already consumed by the *first* `GameManager`) and the *new* `GameManager` created by the reload correctly defaults to `Playing` — exactly like standalone testing, where the flag was never set to begin with.

`PlayerManager` additionally syncs to `GameManager`'s *current* state in its own `Start()` (not just reacting to future events) — cheap insurance against any remaining `Start()`-ordering edge case between it and `GameManager` in the same scene, now that the state itself is decided synchronously and correctly from frame one.

**Accepted, explicitly-flagged limitation**: opening `MainMenu.unity` directly (without `Bootstrap`) and pressing Play will no-op harmlessly — `GameManager.TryGetInstance()` returns `null` since `Prototype.unity` was never loaded, so `EnterPlayingState()` is skipped — rather than launching gameplay. Far less common a testing path than standalone `Prototype.unity`, not worth solving this pass.

## `PlayerManager`'s new gating role

`PlayerManager.Start()` fetches both `GameManager.TryGetInstance()` and `SpawnManager.TryGetInstance()` (`SpawnManager` is already a `GenericSingleton<SpawnManager>`, so this needed no new serialized cross-scene reference), subscribes to `RunStarted`/`ReturnedToMenu`, and immediately syncs to whichever state `GameManager` is already in. `HandleRunStarted()` enables `PlaneController`+`FuelSystem`+`SpawnManager` and `SetActive(true)`s `HUD`; `HandleReturnedToMenu()` reverses all four — the exact same "flip `.enabled`" technique `PlayerManager` already used for `PlaneController` on run-end (`HandleDepleted`/`HandleFlyAway`), extended to three more targets and driven by menu/play state instead of run-end. `HUD` (unlike `SpawnManager`) isn't a singleton, so it's a new `[SerializeField] private GameObject m_hud`, wired the same way `m_followCamera` already is — empty on `Plane.prefab`, set via a `PrefabInstance` modification in `Prototype.unity` pointing at the `HUD` GameObject.

## `MainMenuController`'s Play click

`OnPlayClicked` now, alongside its existing log: hides the menu's own UI immediately (`rootVisualElement.style.display = DisplayStyle.None`, so there's no leftover-menu flash while `GameManager`'s one-frame-delayed transition catches up), calls `GameManager.TryGetInstance()?.EnterPlayingState()`, and fires `SceneManager.UnloadSceneAsync(gameObject.scene)` (fire-and-forget — nothing in this method depends on the unload finishing).

## `RunEnded` carries a cause (UI/art pass, Pass 5a)

`GameManager.RunEnded` is `event Action<RunEndCause>` (`Scripts/Game/RunEndCause.cs`: `OutOfFuel`, `Wrecked`, `FlewTooHigh`, `HitTheDeck`, `OutOfBounds`). Each of the five triggers has its own tiny handler that calls `EndRun(cause)`: `FuelSystem.Depleted` -> `OutOfFuel`, `HealthSystem.Depleted` -> `Wrecked`, `AltitudeSystem.CeilingExceeded` -> `FlewTooHigh`, `AltitudeSystem.GroundHit` -> `HitTheDeck`, `LateralSystem.HardBoundExceeded` -> `OutOfBounds`. `EndRun` keeps the old `IsRunActive` guard, so the first trigger wins and a second one in the same frame cannot overwrite the cause. Subscribers: `GameOverUI` (cause chip), `HudPresenter` (freezes the HUD), `SpawnManager` (stops spawning, ignores the payload). `PlayerManager` still reacts to the underlying system events directly, not to `RunEnded`.

**Lethal hits read WRECKED.** `PlayerManager.HandleDamageDealt` applies the health damage **before** the fuel drain. A hit that empties both (Obstacle_Large deals 10000) used to raise `FuelSystem.Depleted` first, so the first-trigger-wins cause said OUT OF FUEL for a hit that killed the plane. A hit that only empties the fuel (low fuel, small hit) still reads OUT OF FUEL, which is true.

## Pause (Pause, settings & audio, Pass 2a)

`GameManager` has a third state, `PausedState` (`Scripts/Game/States/PausedState.cs`), reached only from `PlayingState` and left only back to it. **It is the only code that pauses by touching `Time.timeScale`**: `OnEnter` sets 0, `OnExit` sets 1. Every gameplay script ticks on scaled time and physics does not step at 0, so the freeze needs no per-system gating (a pure state-gated pause would have meant gating about 13 scripts, freezing the rigidbody and tweens by hand, and a missed system is a silent bug).

- **API.** `Pause()` (ignored unless `IsPlaying`, `IsRunActive` and no request pending), `Resume()` (ignored unless `IsPaused`), `Paused` / `Resumed` events (raised from the state's `OnEnter` / `OnExit`, so `timeScale` is already 0 / back to 1), `IsPaused`. Like `EnterPlayingState`, requests flip a flag and the transition fires on the next `Update` (Update still runs at `timeScale` 0).
- **`IsPaused` includes a pending request** and is false once a resume has started, so handlers of both events see the right value, and a hit-stop ending in the one-frame gap still sees the pause. `IsPlaying` is false while paused (only `PlayerManager.Start` reads it).
- **Resuming is not a new run.** `PlayingState.OnEnter` calls `ConsumeResumeFlag()` (set by `PausedState.OnExit`; the FSM runs `OnExit` before the next `OnEnter`) and skips `RaiseRunStarted()` when it returns true.
- **Hit-stop.** `CameraJuice.HitStopRoutine` leaves the clock alone when `IsPaused` after its real-time wait.
- **`RestartRun()`** sets `timeScale` 1 and reloads the active scene; Game Over RETRY and the pause popup's RESTART RUN both call it. A new `GameManager.Awake` also sets `timeScale` to 1, so a pause cut off by a reload cannot leak.
- **HUD side** (`HudPresenter`): the pause button and Escape (Android back) call `Pause()`; `Paused` shows the popup and `HudView.SetPaused(true)` (releases held joystick / boost, disables the pause button); RESUME starts the 3-2-1 on unscaled time and the game unfreezes at `CountdownFinished` (`Resume()`); back while the popup is open = RESUME, ignored during the countdown. QUIT TO MENU is still a stub (toast, popup comes back); the practice / competitive branching is Pass 2b.
- **Countdown clock.** `HudPausePopup` derives the 3-2-1 from elapsed unscaled time inside one 16 ms scheduled item. An earlier version counted with a 1 s `Every` item created paused; UITK items have a zero first delay, so the first resume of a run fired at once and the countdown began at 2.
- **Not paused:** UITK schedulers and animations (low-fuel flash, popups) run on real time and keep animating behind the popup; cosmetic.
